# 6. UniFi on NAS

> 本教學說明如何在 Synology NAS 上以 **Container Manager**（Docker）部署 [UniFi Network Application](https://docs.linuxserver.io/images/docker-unifi-network-application/)（UniFi Controller），供實驗室管理 UniFi AP、交換器等網路設備。  
> 部署採 **Docker Compose 專案**，同時運行 UniFi 與 MongoDB 兩個容器。

!!! tip "推薦資源"

    Docker 基礎概念請先參閱 O-Week 的 [4. Docker](../oweek/4.docker/)。  
    LinuxServer.io 官方文件：[unifi-network-application](https://docs.linuxserver.io/images/docker-unifi-network-application/)

---

## 1. 背景

### 1-1. 為何需要獨立 Controller？

UniFi 裝置（AP、Switch 等）需由 **Network Application** 集中管理：設定 Wi-Fi、更新韌體、監控連線狀態。  
Ubiquiti 提供 Cloud Gateway 等硬體內建 Controller；若實驗室已有 Synology NAS，也可在 NAS 上以容器自行托管，無需額外購買 Cloud Key。

| 項目 | 說明 |
|------|------|
| **映像檔來源** | `lscr.io/linuxserver/unifi-network-application` |
| **資料庫** | 現行版本**必須**搭配外部 **MongoDB**（不可只跑單一 UniFi 容器） |
| **管理介面** | 瀏覽器開啟 `https://<NAS_IP>:8444`（本教學預設 host 埠 8444） |

---

### 1-2. 架構概覽

```
Synology NAS (Container Manager)
┌─────────────────────────────────────────────────────┐
│  Project: unifi                                     │
│  ┌─────────────────┐    ┌─────────────────────────┐ │
│  │  unifi-db       │◄───│  unifi-network-         │ │
│  │  (mongo:7.0)    │    │  application            │ │
│  │  :27017 (內網)  │    │  Web :8444 → :8443      │ │
│  └─────────────────┘    │  Device :8080           │ │
│                         └─────────────────────────┘ │
└─────────────────────────────────────────────────────┘
         ▲                           ▲
         │                           │
    MongoDB 資料               UniFi AP / Switch（Inform Host → NAS IP）
```

!!! warning "版本與遷移"

    舊版 `linuxserver/unifi-controller`（無 MongoDB）已 deprecated，**無法原地升級**。  
    若從舊版遷移，須在舊 Controller 匯出備份 → 部署新 Compose → 在新 UI 還原。

## 2. 前置條件

!!! abstract "硬體與軟體需求"

    | 項目 | 建議 |
    |------|------|
    | **DSM** | 7.2 以上（內建 Container Manager） |
    | **記憶體** | 至少 2 GB 可用 RAM（UniFi + MongoDB） |
    | **CPU** | x86_64 或 arm64；x86 若用 MongoDB 4.4+ 需 CPU 支援 AVX |
    | **網路** | NAS 建議使用**固定 IP**；裝置 adopt 時需能連到 NAS |

    本教學以 **DS1825+**、DSM 7、Container Manager 實測流程撰寫；其他機型步驟相同，僅 volume 路徑可能不同（常見為 `/volume1/`）。

## 4. 建立目錄與初始化腳本

### 4-1. 目錄結構

在 **File Station** 建立以下結構（路徑可依 NAS volume 調整）：

```
/volume1/docker/unifi/
├── config/              ← UniFi 設定（掛載至容器 /config）
├── init-mongo.sh        ← MongoDB 首次初始化腳本
└── docker-compose.yml   ← Compose 設定（亦可僅在 Container Manager UI 編輯）
```

!!! info "命名慣例"

    資料夾名稱建議使用**小寫**（如 `unifi`），避免部分工具對大小寫敏感。

---

### 4-2. 建立 `init-mongo.sh`

MongoDB 首次啟動時須建立 UniFi 專用使用者與資料庫。  
內容請**直接複製** [LinuxServer.io 官方腳本](https://docs.linuxserver.io/images/docker-unifi-network-application/)，**不要修改**：

```bash
#!/bin/bash

if which mongosh > /dev/null 2>&1; then
  mongo_init_bin='mongosh'
else
  mongo_init_bin='mongo'
fi
"${mongo_init_bin}" <<EOF
use ${MONGO_AUTHSOURCE}
db.auth("${MONGO_INITDB_ROOT_USERNAME}", "${MONGO_INITDB_ROOT_PASSWORD}")
db.createUser({
  user: "${MONGO_USER}",
  pwd: "${MONGO_PASS}",
  roles: [
    "clusterMonitor",
    { db: "${MONGO_DBNAME}", role: "dbOwner" },
    { db: "${MONGO_DBNAME}_stat", role: "dbOwner" },
    { db: "${MONGO_DBNAME}_audit", role: "dbOwner" },
    { db: "${MONGO_DBNAME}_restore", role: "dbOwner" }
  ]
})
EOF
```

!!! warning "腳本注意事項"

    - 檔名須為 `init-mongo.sh`，不可存成 `.txt`
    - 請用 **LF** 換行（勿用 Windows 記事本另存，以免 CRLF 導致 Linux 無法執行）
    - 此腳本**只在 MongoDB 資料庫為空時**執行一次；若之後改密碼或重建 DB，須刪除命名 volume 後重新部署

---

### 4-3. 設定腳本權限（工作排程器）

建立 `init-mongo.sh` 後，**部署前**須設定執行權限並移除可能的 Windows 換行，否則 MongoDB 初始化可能失敗、`unifi-db` 會不斷重啟。

1. **控制台 → 工作排程器 → 新增 → 排程的工作 → 使用者定義的指令碼**
2. **一般**：
    - 工作名稱：例如 `unifi init-mongo 權限`
    - **使用者**：選 **root**
3. **排程**：選「在以下日期執行」→ **不要重複**
4. **工作設定 → 執行指令** 貼上：

    ```bash
    chmod +x /volume1/docker/unifi/init-mongo.sh
    sed -i 's/\r$//' /volume1/docker/unifi/init-mongo.sh
    ```

5. 儲存 → 選中工作 → **執行** → 確認成功

若已設定 Email 通知，執行結果可寄至信箱確認無錯誤；或將輸出寫入檔案：

```bash
chmod +x /volume1/docker/unifi/init-mongo.sh
sed -i 's/\r$//' /volume1/docker/unifi/init-mongo.sh
echo "init-mongo.sh ready" > /volume1/docker/unifi/init-mongo-ready.txt
```

至 File Station 確認 `init-mongo-ready.txt` 已產生。

!!! example "Checkpoint"

    1. `init-mongo.sh` 已存在於 `/volume1/docker/unifi/`。
    2. 已以 **root** 工作排程器執行 `chmod +x` 與 `sed` 指令。

## 5. 查詢 PUID / PGID（無 SSH）

LinuxServer 映像檔需設定 **PUID**（使用者 ID）與 **PGID**（群組 ID），容器才能正確讀寫 `/config` 掛載目錄。  
DSM **沒有圖形介面**直接顯示這組數字；若無法 SSH，可用 **工作排程器** 查詢。

### 5-1. 以 Email 取得結果

1. **控制台 → 工作排程器 → 新增 → 排程的工作 → 使用者定義的指令碼**
2. **一般**：
    - 工作名稱：例如 `查詢 PUID PGID`
    - **使用者**：選 **admin**（或實際建立 `/docker/unifi` 資料夾的帳號）
3. **排程**：選「在以下日期執行」→ **不要重複**
4. **工作設定**：
    - 勾選 **將執行結果以電子郵件寄出**（須先在 **控制台 → 通知 → 電子郵件** 設定 SMTP）
    - **執行指令** 輸入：

        ```bash
        id
        ```

5. 儲存後，選中該工作 → **執行**
6. 查收 Email，輸出類似：

    ```text
    uid=1026(admin) gid=100(users) groups=100(users),101(administrators)
    ```

    | 名稱 | 對應值 |
    |------|--------|
    | **PUID** | `1026`（`uid=` 後的數字） |
    | **PGID** | `100`（`gid=` 後的數字） |

### 5-2. 寫入文字檔（免設定 Email）

**執行指令** 改為：

```bash
id > /volume1/docker/unifi/puid-gid.txt
```

執行後至 File Station 開啟 `puid-gid.txt` 查看。

!!! tip "查詢其他使用者"

    將執行指令改為 `id 使用者名稱`，或在「一般」分頁的使用者下拉選單選擇目標帳號後執行 `id`。

### 5-3. 設定實體路徑權限

!!! warning "避坑指南：若未開權限可能導致server核心設定無法寫入，container重啟後又得重新初始化server"

即使後續在 Docker Compose 中設定了本地路徑映射（`/config`），如果沒有正確賦予容器 NAS 的資料夾權限，UniFi 容器依然無法寫入核心設定檔。這會導致 **「每次重開機都被強制要求重新初始化設定Server」** 的嚴重問題。
請在取得 PUID 對應的使用者帳號後，手動開放權限：

1. 打開 Synology 的 File Station，找到你建立的 unifi 資料夾裡的config檔（路徑為 /volume1/docker/unifi/config）。

2. 對其點擊右鍵 ➔ 內容 ➔ 切換到 權限 頁籤。

3. 點擊 新增，選擇你剛剛查詢到的 PUID 對應的個人信箱帳號。

4. 給予該帳號 讀取 & 寫入 的權限並儲存。

## 6. Docker Compose 設定

### 6-1. 完整 `docker-compose.yml`

以下為 DS1825+ 實測可用的設定。請依實際環境替換 **PUID**、**PGID** 與 **MongoDB 密碼**：

```yaml
services:
  unifi-db:
    image: mongo:7.0
    container_name: unifi-db
    stop_grace_period: 30s
    environment:
      - MONGO_INITDB_ROOT_USERNAME=root
      - MONGO_INITDB_ROOT_PASSWORD=請改成強密碼
      - MONGO_USER=unifi
      - MONGO_PASS=請改成強密碼
      - MONGO_DBNAME=unifi
      - MONGO_AUTHSOURCE=admin
    volumes:
      - unifi-mongo-data:/data/db
      - /volume1/docker/unifi/init-mongo.sh:/docker-entrypoint-initdb.d/init-mongo.sh:ro
    restart: unless-stopped

  unifi-network-application:
    image: lscr.io/linuxserver/unifi-network-application:latest
    container_name: unifi-network-application
    stop_grace_period: 30s
    depends_on:
      - unifi-db
    environment:
      - PUID=1026
      - PGID=100
      - TZ=Asia/Taipei
      - MONGO_USER=unifi
      - MONGO_PASS=請改成強密碼
      - MONGO_HOST=unifi-db
      - MONGO_PORT=27017
      - MONGO_DBNAME=unifi
      - MONGO_AUTHSOURCE=admin
      - MEM_LIMIT=1024
      - MEM_STARTUP=1024
    volumes:
      - /volume1/docker/unifi/config:/config
    ports:
      - 8444:8443
      - 8080:8080
      - 3478:3478/udp
      - 10001:10001/udp
    restart: unless-stopped

volumes:
  unifi-mongo-data:
```

!!! info "密碼設定"

    - 密碼可自訂，但 **`MONGO_PASS` 在 `unifi-db` 與 `unifi-network-application` 必須完全相同**
    - **`MONGO_INITDB_ROOT_PASSWORD`** 為 MongoDB root 密碼，建議與 `MONGO_PASS` 分開設定
    - 請勿留空；若曾以空密碼部署失敗，須刪除命名 volume 後重新部署

!!! info "命名 volume"

    MongoDB 資料使用 Docker 命名 volume `unifi-mongo-data`，可避免 Synology bind mount 常見的 uid 999 權限問題。 (詳情見§9-8) 
    檔案末尾的 `volumes:` 區塊**不可省略**，否則會出現 `undefined volume unifi-mongo-data` 錯誤。

---

### 6-2. 埠映射說明

| Host 埠 | 容器埠 | 協定 | 用途 |
|---------|--------|------|------|
| `8444` | `8443` | TCP | Web 管理介面（HTTPS）；避開 DSM CardDAV 常佔用的 8443 |
| `8080` | `8080` | TCP | 裝置通訊；adopt 時 Inform 須指向此埠 |
| `3478` | `3478` | UDP | STUN |
| `10001` | `10001` | UDP | AP 探索 |

!!! warning "勿映射 1900/udp"

    DSM 系統服務常佔用 **1900/udp**（SSDP/UPnP），映射 `1900:1900/udp` 會導致 UniFi 容器無法啟動。  
    若需 L2 探索，可改試 `1901:1900/udp`；多數情境下省略 1900 仍可正常管理，僅需手動設定 Inform Host。

**請勿**對外映射 MongoDB 的 `27017` 埠。

!!! abstract "部署前確認"

    - [§5](#5-查詢-puid--pgid無-ssh) PUID / PGID 查詢

    4. **繼續 [§8 Override Inform Host](#8-override-inform-host-與裝置-adoption)**——在 Docker 環境下此步驟為**必要**，否則 AP 無法完成 adoption。

## 8. Override Inform Host 與裝置 Adoption

!!! warning "Docker 環境必做"

    Controller 跑在容器內時，預設可能告知 AP 連線至 Docker 內網 IP（如 `172.x.x.x:8080`）。  
    AP 在區網上找不到該位址，就會出現 **Adopting 迴圈**、**斷線後再 Adopting**，且 AP LED 維持**常亮白**（待 adoption）。  
    必須 **Override Inform Host** 為 **NAS 的區網 IP**，並**重啟 UniFi 容器**使設定生效。

### 8-1. 網路拓撲前提

本教學假設 AP 與 NAS 接在同一 router、同一子網，例如：

```
Internet ─ Router (192.168.0.1) ─┬─ NAS / Controller  192.168.0.239
                                 └─ U7 Pro            192.168.0.213
```

| 項目 | 說明 |
|------|------|
| **NAS IP** | Controller 所在位址，Inform Host 須填此 IP（非 Docker 內網 IP） |
| **AP IP** | 與 NAS 須在同一子網（如皆為 `192.168.0.x`） |
| **子網判斷** | `192.168.0.239` 屬 `192.168.0.0/24`，與 `192.168.1.x` **不同子網** |

---

### 8-2. 設定 Override Inform Host

1. 登入 UniFi Web UI：`https://<NAS_IP>:8444`
2. 前往 **Settings → System → Advanced**  
   （部分版本在 **Settings → System → Application Configuration**，或可直接搜尋 **Inform**）
3. 找到 **Inform Host** / **Override Inform Host**
4. **勾選 Override（覆寫）**
5. 填入 **NAS 的區網 IP**（例如 `192.168.0.239`）
6. **儲存**
7. **Container Manager → 容器 → `unifi-network-application` → 重新啟動**

!!! tip "為何要重啟容器？"

    變更 Inform Host 後重啟 UniFi 容器，可避免 AP 仍收到舊的 inform URL（含 Docker 內網 IP）。

---

### 8-3. Adopt 裝置

=== "方式 A — UniFi UI"

    1. 確認 U7 Pro LED 為**常亮白**（待 adoption）
    2. 在 **Devices** 中選取裝置 → **Adopt**
    3. 正常流程：**Adopting → Provisioning → Connected**，LED 變**常亮藍**
    4. 若提示韌體更新，等待完成（LED 可能白/藍閃爍），期間勿斷電

=== "方式 B — SSH 手動 set-inform（建議搭配方式 A）"

    若 UI Adopt 卡住，可 SSH 至 AP 確認 inform URL：

    ```bash
    ssh ubnt@<AP_IP>
    ```

    預設密碼通常為 `ubnt`。登入後：

    ```bash
    info
    set-inform http://<NAS_IP>:8080/inform
    info
    ```

    範例（NAS `192.168.0.239`、U7 Pro `192.168.0.213`）：

    ```bash
    set-inform http://192.168.0.239:8080/inform
    ```

    第二次 `info` 應顯示：

    ```text
    Status: Connected (http://192.168.0.239:8080/inform)
    ```

    若仍為 `http://172.x.x.x:8080/inform`，代表 Override 未生效或未重啟容器，請回到 [§8-2](#8-2-設定-override-inform-host)。

!!! info "8080 埠映射"

    `8080` 須維持 compose 中 `8080:8080` 映射。若 host 埠改為 `8090:8080`，Inform 須改為 `http://<NAS_IP>:8090/inform`。

!!! example "Checkpoint"

    1. Override Inform Host 已勾選，且為 NAS 區網 IP。
    2. 已重啟 `unifi-network-application` 容器。
    3. AP `info` 顯示 inform URL 指向 `http://<NAS_IP>:8080/inform`。
    4. 裝置狀態為 **Connected**，AP LED 為**常亮藍**。

---

### 8-4. 將 AP 設為靜態 IP

Adopt 成功後，建議將 AP 改為 **Static**，避免 DHCP 換 IP 後難以 SSH 或管理。

#### 8-4-1. 進入設定頁面

1. UniFi Web UI → **Devices**
2. 點選 AP（例如 **U7 Pro**）
3. 開啟 **Settings**（或 **Manage** → **Settings**）
4. 找到 **IP Settings**（或 **Network** → **IP Configuration**）
5. 選 **Static**（不要維持 DHCP）

#### 8-4-2. 設定靜態 IP

以下以 **`192.168.0.0/24`** 子網、router Gateway **`192.168.0.1`**、NAS **`192.168.0.239`** 為例。  
請將 IP 改成你環境中**未被占用**的位址：

| 欄位 | 必填 | 填入範例 | 說明 |
|------|:----:|----------|------|
| **IP Configuration** | ✅ | **Static** | 選靜態，勿用 DHCP |
| **IP Address** | ✅ | `192.168.0.210` | AP 固定 IP；勿與 NAS（`.239`）或其他裝置衝突 |
| **Subnet Mask** | ✅ | `255.255.255.0` | `/24` 子網一律填此值 |
| **Gateway** | ✅ | `192.168.0.1` | router LAN IP；**不可留空** |
| **Preferred DNS** | ✅ | `192.168.0.1` | 可填 router IP；或 `8.8.8.8` / `1.1.1.1` |
| **Alternate DNS** | — | `8.8.4.4` | 選填；可留空 |
| **DNS Suffix** | — | （留空） | 家用／實驗室通常不需要 |

**填完後按 Apply / Save**，AP 會短暫斷線並以新 IP 重新連線；LED 應維持**常亮藍**。

!!! warning "常見錯誤"

    | 錯誤 | 後果 |
    |------|------|
    | **Subnet Mask / Gateway 留空** | AP 無法對外連線，韌體更新、NTP 失敗 |
    | **IP 與 NAS / router 衝突** | 網路不穩或無法連線 |
    | **Gateway 填成 NAS IP** | AP 無法上網；Gateway 應為 **router**，不是 Controller |

!!! tip "靜態 IP 選址"

    - 建議選 router DHCP 池**以外**的位址，或於 router 對 AP MAC 做 **DHCP 保留**
    - 變更 IP 後，SSH 須改用新位址，例如 `ssh ubnt@192.168.0.210`
    - Inform Host 仍指向 **NAS IP**（`192.168.0.239`），與 AP 靜態 IP 無關

!!! example "Checkpoint"

    1. AP 在 **Devices** 中顯示固定 IP（如 `192.168.0.210`）。
    2. 狀態 **Connected**，LED **常亮藍**。
    3. 同子網電腦可 `ping 192.168.0.210`。

## 9. 常見問題

### 9-1. `driver failed programming external connectivity`

代表 **Host 埠已被佔用**。Synology 常見衝突：

| 埠 | 常見佔用者 |
|----|------------|
| `8443` | CardDAV Server |
| `1900/udp` | DSM SSDP / UPnP |
| `8080` | 其他容器或套件 |

**排查（工作排程器，使用者 root，執行一次）：**

```bash
netstat -tulpn | grep -E ':(8080|8443|8444|1900|3478|10001) ' > /volume1/docker/unifi/port-check.txt
```

至 File Station 查看 `port-check.txt` 中 **LISTEN** 的埠，調整 compose 映射或關閉衝突服務。

**逐步加回埠**：若不確定哪個埠衝突，可先只保留 `8444:8443` 確認能啟動，再逐一加回 8080、3478、10001。

---

### 9-2. AP 卡在 Adopting 迴圈 / LED 常亮白

| 現象 | 可能原因 |
|------|----------|
| Adopting → 斷線 → 再 Adopting | Inform Host 未 Override，AP 收到 Docker 內網 IP |
| LED **常亮白** | 尚未 adoption 成功（成功後通常為**常亮藍**） |

**處理步驟：**

1. 依 [§8-2](#8-2-設定-override-inform-host) 設定 Override 並重啟 UniFi 容器
2. 確認 compose 已映射 `8080:8080`、`3478/udp`、`10001/udp`
3. 從同子網裝置測試 `http://<NAS_IP>:8080` 可連線（非 timeout）
4. SSH 至 AP 執行 `set-inform http://<NAS_IP>:8080/inform`，以 `info` 確認 URL 正確
5. 仍失敗時，Forget 裝置 → 長按 AP Reset → 重新 Adopt

---

### 9-3. `unifi-db` 不斷重啟（exitCode 100）

| 原因 | 解法 |
|------|------|
| 跳過 [§4-3](#4-3-設定腳本權限工作排程器) | 重新以 root 工作排程器執行 `chmod +x` 與 `sed` |
| 未設定 MongoDB 密碼 | 在 YAML 設好密碼，`MONGO_PASS` 兩容器一致 |
| 命名 volume 含錯誤初始化資料 | **Container Manager → 磁碟區**，刪除 `unifi-mongo-data` 後重新部署 |

**重建流程：**

1. 停止 unifi 專案  
2. 刪除命名 volume `unifi-mongo-data`  
3. 確認 [§4-3](#4-3-設定腳本權限工作排程器) 已執行  
4. 確認 YAML 密碼已設定 → 重新部署  

---

### 9-4. `undefined volume unifi-mongo-data`

`unifi-db` 使用了命名 volume，但 compose 檔**缺少**底部宣告：

```yaml
volumes:
  unifi-mongo-data:
```

補上後重新部署即可。

### 9-5. Web UI 無法連線

- 確認使用 **`https://` 與正確 host 埠**（本教學為 `8444`）
- 等待容器完全啟動（查看 `unifi-network-application` 日誌）
- 確認 `unifi-db` 已穩定運行（UniFi 依賴 MongoDB）
- **控制台 → 安全性 → 防火牆**：允許 8444、8080 等埠

### 9-6. 更新與備份

- **更新**：Container Manager → 專案 → 重建／拉取新映像；更新前請在 UniFi UI **匯出備份**
- **備份**：UniFi 設定備份 + 命名 volume `unifi-mongo-data` + `/volume1/docker/unifi/config/`
- MongoDB 映像請**固定版本 tag**（如 `mongo:7.0`），勿用 `latest`（主版本不可自動升級）

### 9-7. 每次重啟容器都被強制要求重新設定server帳密（完全失憶）
此情況是因為 UniFi 容器沒有權限將核心設定檔寫入 NAS 實體硬碟(`/config`)所致。

解法：

請回到 §5-3. 設定實體資料夾權限，確認config 資料夾的權限已開放給 PUID 對應的使用者帳號才能順利寫入存檔。

### 9-8. 進階補充：為何資料庫不使用實體路徑掛載？

在 Docker 的使用習慣上，將所有資料都掛載到 NAS 的實體資料夾（Bind Mount）便於備份。但在本教學中，我們的架構採用了**「混合式掛載」**： 

- **主程式設定 (`/config`)** ➔ 掛載於實體路徑（方便備份與修改）。

- **資料庫 (`/data/db`)** ➔ 使用 Docker 命名卷（Named Volume `unifi-mongo-data`）。

這是為了避開最常遇到的 **「UID 999 權限問題」**，原因如下：

1. - 我們使用的 UniFi 主程式映像檔（`linuxserver`）非常貼心，支援透過 `PUID` 與 `PGID` 變數來指定寫入權限，因此只要把(`/config`) 開權限給`PUID`對應使用者即可。
    - 然而，**官方的 `mongo:7.0` 映像檔並不支援 `PUID/PGID`**。它在容器內部被強制規定只能使用一個名為 `mongodb` 的內建帳號來運行，而這個帳號的 UID 固定為 **999**。

2.   - 如果我們將資料庫強制掛載到 NAS 的實體資料夾（例如 `- /   volume1/docker/db:/data/db`），**MongoDB 啟動時會以「UID 999」的身分試圖寫入 NAS 硬碟**。

    - 由於你的 NAS 系統中通常不存在 UID 999 這個使用者，NAS 系統的資安防護會直接拒絕寫入。這將導致 MongoDB 容器啟動失敗，並不斷拋出 `Permission Denied` 或 `Exit Code 100` 的錯誤而無限重啟。

 3.     解法與最佳實踐
    若堅持要使用實體路徑，管理者必須透過 SSH 進入 NAS，強制將該資料夾的擁有者改為 999（執行 `chown -R 999:999 /volume1/docker/db`），這大幅增加了架設的技術門檻。

因此，**將資料庫交給 Docker 命名卷（Named Volume）管理是此架構下的最佳實踐**。Docker 系統會在底層自動用最高權限處理好這堆二進制檔案的讀寫問題，確保部署流程順暢且不會報錯！
